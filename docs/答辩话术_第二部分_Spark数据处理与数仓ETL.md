# 第二部分「Spark 数据处理与数仓 ETL」答辩话术

> 适用场景：睡眠健康大数据平台答辩，角色分工为第 2 部分。  
> 建议时长：3~4 分钟。  
> 准备要求：结合 PPT 第二页或数据流图讲解，配合 `run_pipeline.py` 架构图效果更佳。

---

## 一、角色定位（10 秒）

> “大家好，我负责的是**第二模块：Spark 数据处理与数仓 ETL**。如果把整条平台数据流比作一条流水线，那第一部分搭好了厂房和机器，我这一环就是**把原材料洗干净、分类、打包**，然后分别送到仓库、货架和下游机器——也就是 MySQL、Elasticsearch 和后续机器学习模块。只有我这环数据质量过硬，后面的大屏、预测、检索才能靠谱。”

---

## 二、核心工作三句话（15 秒）

> “我的工作可以概括为三句话：**数据清洗与特征工程、数仓分层与指标聚合、多引擎数据分发**。最终产出干净明细、汇总报表、可检索索引三类数据资产，供后端 API 和大屏直接调用。”

---

## 三、3~4 分钟完整答辩话术（重点背诵）

### 1. 数据底座与整体链路（30 秒）

> “在基础架构跑起来之后，我通过 **PySpark 单 Session 链式管道** `run_pipeline.py` 把数据从本地 CSV 上传到 HDFS，然后依次完成 Hive 数仓建表、清洗、聚合、同步，最后写进 MySQL 和 Elasticsearch。整个过程跑在一个 SparkSession 里，避免了多次 `spark-submit` 反复启停 JVM 的开销。”

### 2. 数仓分层：ODS → DWD → DWS → ADS（45 秒）

> “数仓采用标准四层架构：
> - **ODS 层**：贴源存储原始 CSV，保留全字段，不做业务改造，方便回溯；
> - **DWD 层**：清洗后的明细事实表，做去重、空值过滤、衍生字段计算，是后续分析的核心；
> - **DWS 层**：轻度聚合，比如按年/月趋势、地区、设备型号、年龄段做汇总；
> - **ADS 层**：面向应用的结果表，比如相关性矩阵、温度-效率分桶、睡前运动对比等，直接对应后端接口和大屏图表。”

### 3. 数据清洗与特征工程（45 秒）

> “在 ODS → DWD 的清洗阶段，我主要做了四件事：
> 1. **去重过滤**：按 `user_id` + `date_recorded` 去重，过滤掉时长、评分、年龄为空或异常的记录；
> 2. **时间提取**：从日期字段衍生出 `year_recorded`、`month_recorded`；
> 3. **人口学特征**：根据年龄分桶得到 `age_bucket`（18-30、30-45、45-60、60+），并按身高体重计算 **BMI**；
> 4. **地域维度**：根据 timezone 字段解析出 `region`（亚洲、欧洲、北美洲等），为后续世界地图大屏提供维度。
> 这些字段都是后续按地区和人群做统计分析的基础。”

### 4. DWS/ADS 统计指标聚合（45 秒）

> “在 DWS 层，我计算了平台大屏需要的核心指标：
> - **年度/月度趋势**：平均睡眠评分、平均睡眠效率、失眠率、高呼吸暂停风险人数；
> - **地域分布**：各地区平均睡眠时长与评分；
> - **设备份额**：各智能手表型号占比；
> - **年龄段睡眠阶段**：深睡、浅睡、REM、清醒占比；
> - **打鼾-血氧气泡图**：抽样明细用于屏 3 气泡图展示。
> 在 ADS 层，我进一步产出 Pearson 相关性矩阵、温度-睡眠效率分桶、睡前运动 vs 入睡潜伏期对比等分析表，这些数据直接对应后端 RESTful 接口。”

### 5. 多引擎数据分发（30 秒）

> “为了让数据能被下游模块高效使用，我做了两次分发：
> - **MySQL 同步**：把 14 张 DWD/DWS/ADS 结果表通过 JDBC 写入 MySQL，供 Spring Boot 接口做毫秒级查询；
> - **Elasticsearch 同步**：把 DWD 清洗明细通过 ES Bulk API 写入 `sleep_records` 索引，构建近 6 万条可检索文档，支持屏 5 的多条件极速搜索和实时聚合统计。”

### 6. 收尾与价值总结（15 秒）

> “所以第二部分的关键词是**清洗、建模、分层、分发**。它承上启下：向上接 Docker + HDFS + Hive 基础架构，向下为机器学习、后端服务、前端大屏提供高质量、可直接消费的数据资产。谢谢大家。”

## 六、常见答辩提问与建议回答

### Q1：为什么要做 ODS/DWD/DWS/ADS 四层？
> “四层架构是数据仓库的标准实践。ODS 保留原始数据方便审计回溯；DWD 做统一清洗，保证口径一致；DWS 做轻度聚合，减少重复计算；ADS 面向应用，直接对接接口。这样任何一层改动都不会影响其他层，耦合低、可维护性强。”

### Q2：为什么选择 MySQL 和 Elasticsearch 双写？
> “MySQL 适合结构化、关联查询和事务性操作，比如后端按用户 ID 查画像；Elasticsearch 适合模糊检索、多条件过滤和实时聚合，比如屏 5 的搜索页。两种存储各司其职，避免单一数据库既要 OLTP 又要全文检索。”

### Q3：数据清洗过程中怎么处理异常值？
> “我们主要做了三步：去重、过滤空值、按业务规则截断（比如睡眠评分限制在合理区间 42~100，BMI 按身高体重公式计算，年龄必须大于 0）。更复杂的异常检测可以后续用机器学习做，但 ETL 阶段先保证基础可用性。”

### Q4：ETL 跑一次大概多久？
> “在本地 Docker 环境下，整条管道从 HDFS 上传、Hive 建表、清洗聚合、ML 训练、到写入 MySQL/ES，总耗时在几十秒到两分钟左右，具体取决于机器性能。我们用单一 SparkSession 串联，减少了 JVM 冷启动开销。”

### Q5：DWS 和 ADS 怎么区分？
> “DWS 是公共汇总，面向多个下游复用；ADS 是面向具体应用的窄表，比如温度-效率、睡前运动对比，就是直接为了屏 3 的某张图表服务的。”
